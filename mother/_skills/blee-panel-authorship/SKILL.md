# Blee-Panel Authorship for bisos-pip Packages

Every bisos-pip package has a **primary Blee-Panel** at:

```
py3/panels/<pkg-name>/_nodeBase_/fullUsagePanel-en.org
```

Blee-Panels are the most permanent and most important form of documentation
in the BISOS/Blee ecosystem — more permanent than `README.org`, more
permanent than `AI-DevStatus.org`. They are the developer's primary
in-environment usage surface. When they're wrong, users are wrong.

## The one rule about content

**Do NOT hand-edit content between `####+BEGIN:` and `####+END:` markers.**
The body between markers is *generated by Blee/Emacs dblock machinery* when
the panel is opened in Emacs. Author only:

1. The `####+BEGIN:` header line (signature + `:key value` parameters)
2. The plain-org content *between* dblocks (section text, TODO items, etc.)
3. Placeholder content between markers *only* until Emacs regenerates it

If a dblock body needs to change, update the header parameters. See the
`dblock-authoring` skill for the full mechanics.

## Standard panel skeleton (in order)

1. **File header** — one `* B|` line, then standard header dblocks:

   | Dblock                                    | Purpose                                |
   |-------------------------------------------|----------------------------------------|
   | `bxPanel:common/title-plus`               | Panel title + roam metadata            |
   | `blee:bxPanel:topPanelControls`           | Blee navigation controls               |
   | `blee:bxPanel:title`                      | Formatted title line with ByStar logos |
   | `blee:bxPanel:terseTreeNavigator`         | Folding TOC of decedents/siblings/ancestors |

   These are boilerplate — copy the exact header from an existing
   bisos-pip panel (e.g. `bisos.aiActivity`, `bisos.gitist`) and only
   change the `#+title`, `#+roam_key`, and node-path values.

2. **Overview section** — a `blee:bxPanel:foldingSection` with
   `:title "Overview" :anchor "Panel"`, followed by one paragraph
   describing what the package does. Also point at the package's
   `README.org` panel entry.

3. **Package Installation section** — `blee:bxPanel:foldingSection` titled
   "Pip and Pipx Package Installation", containing two `blee:bxPanel:runResult`
   dblocks:
   - `:command "pipx install bisos.<pkgname>"`
   - `:command "pipx uninstall bisos.<pkgname>"`

   Use `:results "none"` on install/uninstall (no captured stdout —
   they're actions).

4. **Main command intro** — `blee:bxPanel:foldingSection` for the `.cs`
   executable, containing a `blee:panel:icm:py:intro` dblock. This shows
   the command's self-described usage:
   ```
   :icmName "<pkgname>.cs" :comment "Examples Menu" :afterComment "-- -i examples"
   ```

5. **Feature sections** — one `blee:bxPanel:foldingSection` per logical
   group of commands. Each contains either:
   - `blee:bxPanel:runResult` dblocks for **read-only / query commands** —
     the command is executed when the dblock is regenerated and the output
     is captured in the file (`:results "stdout"`).
   - `blee:panel:icm:py:cmnd` dblocks for **action commands** — a clickable
     button in Blee that runs the command interactively.

   Order: read-only commands before action commands within a section.

6. **User Config section** (if the package uses `bisos.b.userConfig_csu`) —
   `blee:bxPanel:foldingSection` titled "User Config --- Persistent Parameters":
   - One `blee:bxPanel:runResult` per persistent param, invoking
     `userConfig_get --parName=<name>` with `:results "stdout"` — shows the
     current value inline.
   - One `blee:panel:icm:py:cmnd` per param invoking
     `userConfig_set --parName=<name> --parValue=<value>` for setting it.

7. **Design and Evolution TODOs** — `blee:bxPanel:evolution` dblock
   followed by a `blee:bxPanel:foldingSection` titled "Design and Evolution"
   containing org TODO items for planned improvements.

8. **Standard footer dblocks** (also boilerplate — copy from an existing
   panel):

   | Dblock                                | Purpose                            |
   |---------------------------------------|------------------------------------|
   | `blee:bxPanel:evolutionMaintainers`   | Bug-reports + maintainer contact   |
   | `blee:bxPanel:footerPanelControls`    | Closing navigation controls        |
   | `blee:bxPanel:footerOrgParams`        | Org-mode local params              |
   | `blee:bxPanel:footerEmacsParams`      | Emacs file-local variables         |

## Dblock choice: `icm:py:cmnd` vs `runResult`

Use this decision table:

| The command is...                     | Dblock                              |
|---------------------------------------|-------------------------------------|
| Read-only, quick, output worth seeing | `blee:bxPanel:runResult :results "stdout"` |
| Action with side effects              | `blee:panel:icm:py:cmnd`            |
| Install / uninstall                   | `blee:bxPanel:runResult :results "none"`   |
| Long-running or interactive           | `blee:panel:icm:py:cmnd`            |

`runResult` bakes captured output into the panel — great for
"show me what this produces" documentation. `icm:py:cmnd` is a clickable
button.

## Clickable shell commands: how a panel runs a command

Every command button in a panel, whichever dblock writes it, comes down to one org link:

```org
[[elisp:(lsip-local-run-command "vscodeClaude.cs -i hooksCheck")][vscodeClaude.cs -i hooksCheck]]
```

`lsip-local-run-command` (blee/env3 `legacy/lsip-basic.el`) types the command into the comint shell
buffer `*LSIP* localhost`, presses Enter and shows that buffer. So the command runs in a
real interactive bash: your environment and aliases apply, the output stays in the shell buffer for
scrolling and rerunning, a long-running command can be watched or interrupted, and a `sudo`
prompt can be answered. Things to know:
- The *Results* line of every panel's top controls (Here, Below, Right, Other, Popup) and its
  *Window* setting (0-3, `blee:bnsm:results-window-set`; the default is 2, split below) decide where
  the shell buffer appears.
- It runs in the shell's own current directory, not the panel's. `lsip-local-run-command-here`
  first sends `pushd <the panel buffer's default-directory>`: use it when the command depends on
  where it runs (the `lsf`, `pwd` and `pushd` buttons of the top controls are its common uses).
- The command is typed, not quoted: keep `"` out of it, or escape it as `\"` inside the elisp
  string.

Seven dblocks write such buttons. Their writers are in
blee/env3 `dblocks/dblock-org-general.el`:

| Dblock                      | Header keys                  | Writes                                |
|-----------------------------|------------------------------|---------------------------------------|
| `blee:bxPanel:runResult`    | `:command :results`          | the button, plus the output (below)   |
| `blee:panel:unix:cmnd`      | `:label :command :folding?`  | one button for any shell command      |
| `blee:panel:unix:cmndIntro` | `:label :command`            | `cmd`, `Man`, `cmd --help`            |
| `blee:panel:icm:bash:cmnd`  | `:label :icmName`            | one button for a Bash ICM invocation  |
| `blee:panel:icm:bash:intro` | `:label :icmName`            | examples, visit, `which -a`, describe |
| `blee:panel:icm:py:cmnd`    | `:label :icmName`            | one button for a PyCS invocation      |
| `blee:panel:icm:py:intro`   | `:label :icmName`            | examples, visit, describe             |

All take `:outLevel :sep :comment :afterComment` too. Examples, as found in panels:

```org
####+BEGIN: blee:panel:unix:cmnd :outLevel 2 :sep nil :folding? nil :label "info" :command "sudo netstat -plnt" :comment "Open Ports, pid/cmnd" :afterComment "-- Diagnostic"
####+BEGIN: blee:panel:unix:cmndIntro :outLevel 1 :sep nil :folding? nil :label "Cmnd" :command "nmcli" :comment "Network Manager" :afterComment "L2+L3"
####+BEGIN: blee:panel:icm:bash:cmnd :outLevel 1 :sep t :folding? t :label "BinsPrep" :icmName "lcaSynergySrcBinsPrep.sh -i fullUpdate" :comment "Source BinsPrep" :afterComment ""
####+BEGIN: blee:panel:icm:py:cmnd :outLevel 1 :sep t :folding? nil :label "PyCS" :icmName "marmeeDaemonSysd.cs --cls=sysdUnitMarmee  -i sysdUserUnit status" :comment "" :afterComment ""
####+BEGIN: blee:bxPanel:runResult :outLevel 1 :command "dnsip www.example.com"  :results "stdout" :comment "" :afterComment ""
```

**`runResult` runs the command twice over.** The button runs it in `*LSIP* localhost`, as above.
Separately, *regenerating* the dblock (its `D-Run` button, `blee:org-update-named-dblocks-above`,
or Update Buf Dblocks) runs it with `shell-command-to-string` and writes the output into the
panel, under a "Last Executed at: ... by: ... on: <host>" line:
- `:results t` (or no `:results`): output captured; `:results "stdout"` is labelled "stdout",
  but the writer does not actually drop stderr (the `2> /dev/null` it prepares is unused).
- `:results nil` or `"none"`: only the button; regenerating runs nothing.
- So regenerating a panel runs every `runResult` command with results. Give results only to
  read-only, quick commands. An action goes in a `cmnd` dblock, or in `runResult` with `"none"`.
- `echo <command>` as the `:command` is the panel idiom for "edit before running": the
  click prints the line in the shell buffer, ready to edit and run (common for intrusive commands).

**Writing buttons by hand: `bashRun:` and `bashRunHere:`.** Between dblocks (in plain org text, a
TODO, a list of steps) write the command as the link itself:

```org
[[bashRun:vscodeClaude-assemble.cs -i fullCheck]]
[[bashRunHere:lsf]]
[[bashRun:vscodeClaude-assemble.cs -i fullUpdate][Assemble]]
```

These org link types (blee/env3 `legacy/lsip-basic.el`, 2026-11-02) call `lsip-local-run-command`
and `lsip-local-run-command-here` on the link's path, trimmed. Without a description the link
displays as itself (`bashRun:...`), which tells the reader a click runs it. A `]` in the command
needs org's backslash escape. They are the short form of what the dblocks still write,
`[[elisp:(lsip-local-run-command "...")][...]]`, which keeps working. An elisp function is linked
directly: `[[elisp:(b:vscode/init)][b:vscode/init]]`. On GitHub any of these shows as plain text.

## Common dblock header parameters

**`blee:bxPanel:foldingSection`**:
```
:outLevel 1 :title "<Section Title>" :anchor "<Anchor>" :extraInfo "<subtitle>"
```
`:outLevel` is the panel's document structure: `0` is a *part*, `1` a *chapter*, `2` a section
within a chapter. Most panels have no parts: their sections are chapters, `:outLevel 1`, all
siblings (as the Overview's is). Use `:outLevel 0` only in a panel that really groups chapters
into parts. `:sep t` adds a separator line above; `:sep nil` omits it. `:anchor` becomes an
`<<Anchor>>` target for cross-references.

**`blee:panel:icm:py:cmnd`**:
```
:outLevel 1 :sep t :folding? nil :label "Direct" :icmName "<full command>"
:comment "<one-line description>" :afterComment ""
```
Set `:sep t` on the first cmnd in a section, `:sep nil` on subsequent ones
in the same section. `:folding? nil` keeps the cmnd inline (not collapsed).

**`blee:bxPanel:runResult`**:
```
:outLevel 1 :sep t :command "<full command>" :results "stdout"|"none"
:comment "<description>" :afterComment ""
```
`:results "stdout"` captures the command's output into the block body when
the dblock is regenerated (stderr too, in practice; see above). `:results "none"` writes only the
button: regenerating runs nothing, and clicking runs the command in the shell buffer.

## What to include vs. exclude

Include only what the package *currently* provides:

- Command-only packages: **no** RO, performer, daemon, or service sections.
- Every `icm:py:cmnd` or `runResult` dblock must map to a real, existing
  invocation. If the command doesn't exist yet, don't add its dblock.
- If the package has `userConfig` params, one row per param — no more, no
  less.

## Regenerating panels

Open the panel in Blee and use the "Update Buf Dblocks" panel control
(elisp `org-dblock-update-buffer-bx`). This regenerates every dblock in
the buffer, running each command and capturing output. Save the buffer to
persist.

For pure-Python regeneration of the `b:ai:file/particulars` dblock
specifically, use `py-dblock.cs updateDblocks <file>` (from
`bisos.pyDblock`). But most panel dblocks require Emacs — regenerate in
Blee.

## Common pitfalls

- **Lines over 105 characters, tables included.** Panels are read in Emacs windows.
  Keep every line, every table row too, at 105 or less; move long values (paths, command
  lines) out of tables into a list below. Full rule and check: the `readme-authorship` skill.
- **Panels shipped with stale captured output.** `runResult` bakes stdout
  into the file. If the command's output changes and the panel isn't
  regenerated, the panel lies to users. When behavior changes, regenerate
  the panel and commit the update.
- **Panels shipped without regeneration.** A freshly-authored panel has
  placeholder content inside dblocks until Emacs regenerates them. Always
  open in Blee and regenerate before committing.
- **`_nodeBase_/` symlink** — `/bisos/panels/bisos-core/bisos-pip/<pkg>/`
  usually contains a symlink to the package's `py3/panels/<pkg>/_nodeBase_/`.
  Update the package's panel first; the `/bisos/panels/` view follows
  automatically.

## What NOT to do

- Do NOT hand-edit dblock body content — regenerate.
- Do NOT include panel sections for commands that don't exist yet.
- Do NOT copy an entire panel from another package without updating the
  header (`#+title`, `#+roam_key`, the "This File" path, the "auto" title
  block). A copy with a wrong `#+roam_key` corrupts the panel graph.
- Do NOT add RO / performer / daemon sections to command-only packages.
