# README.org Authorship

Every bisos-pip repo has two README files, but only one is authored:

- **`README.org`** — the *source*, authored in org-mode, at the repo root.
  Human-oriented. Claude authors and maintains this file.
- **`py3/README.rst`** — the *generated* PyPI-facing form. **Produced by
  `py3/pypiProc.sh` during release** (specifically `pypiProc.sh -i fullPrep`,
  which updates both `_description` and `README.rst` from `../README.org`).
  **Never hand-edit `README.rst`.** Any edits will be overwritten by the
  next release.

**`README.org` is the only authored source.** Claude edits `README.org`;
`README.rst` gets regenerated by the release tooling. If you notice
`README.rst` is stale relative to `README.org`, that's fine — it'll be
current after the next release run. Do not attempt to "sync" it manually.

## Standard section structure

For a **command-only PyCS package** (no RO/service/daemon layer), the
canonical `README.org` skeleton is:

1. **Header** — `#+title`, `#+DATE`, `#+AUTHOR`, `#+OPTIONS: toc:4`
2. **Top Controls dblock** — `#+BEGIN: b:org:pypi:readme/topControls` with
   `:pkgName "<pkgname>" :comment "basic"`
3. **Overview** — one paragraph: what the package does, in the developer's
   voice
4. **TOC** — `* Table of Contents     :TOC:` (org-mode auto-generates)
5. **Part of BISOS — ByStar Internet Services Operating System** — standard
   BISOS/ByStar boilerplate linking to the ecosystem (see below)
6. **`<package> is a Command-Only PyCS Facility`** — explains the package
   is a CLI tool via PyCS-Framework, links to `bisos.b`
7. **Post-Installation Setup** — user-config initialization if applicable
   (`userConfig_set --parName=... --parValue=...`)
8. **Installation** — subsections for pip and pipx; list the commands the
   package installs
9. **Usage** — one subsection per major operation. Each shows the CLI
   invocation as a `#+begin_src bash` block
10. **Key Files** — the `py3/bin/` and `py3/bisos/<pkg>/` files that matter,
    with one paragraph each
11. **Documentation and Blee-Panels** — points at
    `py3/panels/<pkg>/_nodeBase_/fullUsagePanel-en.org`
12. **Support** — standard Mohsen Banan contact block
13. **Planned Improvements** — org TODO items for open work

**Do NOT include** RO, performer, daemon, service, or worker sections in
command-only packages.

## How `README.rst` gets generated

`py3/pypiProc.sh` handles the `README.org` → `README.rst` conversion as
part of the release workflow. The relevant commands (invoked by the
`bisos-pip-release` skill and by manual release runs):

- **`pypiProc.sh -i fullPrep`** — updates both `_description` and
  `README.rst` from `../README.org`. Run this before every PyPI upload.
- **`pypiProc.sh -i fullPrepBuild forPypi`** — full release build path;
  calls `fullPrep` as part of the sequence.
- **`pypiProc.sh -i readmeToDescriptionOrg ../README.org ./_description.org`**
  — the `README.org` → `_description.org` step used inside `fullPrep`.

The conversion under the hood uses pandoc (`pandoc --from=org -s -t rst
--toc README.org -o README.rst`), but you should not invoke pandoc directly
— go through `pypiProc.sh` so the surrounding steps (`_description` update,
setup.py regeneration, etc.) stay in sync.

**Rule of thumb:** if you find yourself typing `pandoc` or opening
`README.rst` in an editor, stop. Edit `README.org` instead, then let
`pypiProc.sh` regenerate `README.rst` at release time.

## Line width: 105 characters, tables included (user rule)

Human-oriented org files are read in Emacs windows, not on a wide web page. **No line may
exceed 105 characters --- tables included.** Wrap prose at about 100. This applies to
`README.org`, Blee panels, `AI-*.org` files and any other org document written for people.

Tables are where the limit is usually broken. To keep one under 105:

- Keep cells short: a label, a number, a state. Move long values (absolute paths, command
  lines, JVM flags, URLs) out of the table into a short list right below it, keyed by the
  row's first cell.
- Drop a column that only restates the row name or the section text (e.g. =bisos.<name>= when
  the section already says the packages are =bisos.<name>=).
- Split a table that needs two kinds of information into two tables.
- Align by the raw characters: org does not hide the `=`/`~` markers by default, so pad as if
  they are visible, and make every row of a table the same length.

Check before handing a file over --- the aligner pads every table by raw characters and lists every
line over 105 (dblocks and example/src blocks are left alone):

```bash
python3 <skills>/cbm-package-authorship/tools/orgTableAlign.py README.org          # align + report
python3 <skills>/cbm-package-authorship/tools/orgTableAlign.py README.org --check  # report only
```

Tables holding org links (`[[target][description]]`) are aligned by Emacs on their *displayed* width; the
aligner pads by raw characters and would widen and misalign them. On such a file use `--check` only, and
align those tables in Emacs (`C-c C-c` in the table). Found on `ai-templates/README.org`'s activity table.

## Several READMEs describing the same thing

A repo's README often describes commands that another repo's README also needs (a Python
package's commands, and the Blee package that wraps them):

- *One owner per table.* The README of the repo that has the commands holds the full table; the
  other summarizes (the names, one line each) and links to that section. Two copies drift.
- *Link across repos by GitHub anchor*:
  `[[https://github.com/bisos-pip/aiActivity#prompt-a-vs-code-claude-session-vscodeclaudecs][Prompt a VS Code Claude Session]]`.
  The anchor is the heading, lowercased, spaces to `-`, punctuation dropped --- as the `:TOC:`
  entries show. Renaming a heading breaks the links to it.
- *An org target in another file is not a link*: `[[10.9]]` in a README points to a `<<10.9>>`
  of the README itself. Write `WorkPlan 10.9`, or a `file:` link.
- *Cross-link both ways*, and say in each what the other holds.

A Blee package's README (a blee-pkg) follows its siblings' frame (`aiplus`), not the bisos-pip
skeleton above; the line-width rule applies to both. See the blee-pkg AI-Activity.org.

## Table of Contents

`README.org` uses the `:TOC:` tag on the Table of Contents heading. The
`toc-org` package regenerates the TOC on save. If you add or reorder
sections, the TOC updates automatically — but only in Emacs. If editing
outside Emacs, either regenerate manually or note that the TOC will refresh
next time the file is opened in Emacs.

## Common pitfalls

- **Don't hand-edit `README.rst`.** It's generated by `pypiProc.sh -i
  fullPrep` — your edits will be silently overwritten at release time.
- **Don't invoke `pandoc` yourself.** Go through `pypiProc.sh` so
  `_description` and other release artifacts stay in sync.
- **Don't hand-write PyPI badges into `README.org`.** The top-controls
  dblock handles PyPI and GitHub links.
- **PyPI RST rendering is strict.** Broken RST (from a malformed
  `README.org` that pandoc converts wrong) shows as a plain-text README on
  PyPI. Test the conversion by uploading to Test-PyPI first (see the
  `bisos-pip-release` skill).
- **`py3/README.rst` is what `setup.py` reads for `long_description`.** If
  `pypiProc.sh -i fullPrep` wasn't run before the upload, the PyPI page may
  show a stale README (last-generated content, not the current
  `README.org`).

## What NOT to do

- Do NOT edit `py3/README.rst` — it is generated, not authored. Edit
  `README.org` instead.
- Do NOT try to "sync" `README.rst` to `README.org` by hand. Run
  `pypiProc.sh -i fullPrep` at release time; between releases, staleness
  is expected and harmless.
- Do NOT invoke `pandoc -f org -t rst` directly to update `README.rst`. Go
  through `pypiProc.sh` so associated artifacts (`_description`, setup.py)
  regenerate together.
- Do NOT include emojis or decorative unicode in `README.org` unless the
  developer explicitly requested it.
- Do NOT add RO / service / daemon sections to a command-only package's
  README.
- Do NOT link to internal `/bisos/panels/...` paths in the README — those
  are BISOS-internal and won't render for users reading on GitHub or PyPI.
  Link to public URLs and to `./py3/panels/...` (relative) instead.
